DevSecOps Architecture — Strata.Cloud

Strata Pipeline Blueprint

A build-once, promote-everywhere CI/CD design for the eight-service strata-cloud monorepo: language-detected tests and security scanning gate every build, one reusable build-and-sign stage feeds ECR, and three environment-scoped deploy pipelines never rebuild what CI already produced.

  • root: wanda-altcloud/.github/
  • environments: develop UAT prod
  • compute: ECS Fargate
  • registry: ECR, immutable tags
Prerequisite — verified, not yet applied

None of this can run from where the pipeline files live today. GitHub only reads .github/workflows/ and .github/dependabot.yml from the literal root of the repository. wanda-altcloud is the one real repo (confirmed via its origin remote and the single top-level .git) — but both strata-cloud/.github/ and application-ci-cd/.github/ are nested subfolders, and there is no .github/ at the true root at all.

Every workflow proposed below is written to live at wanda-altcloud/.github/workflows/. Nothing here has been moved, committed, or pushed yet.

How a commit becomes a running task

One build pipeline runs on every push to develop or uat and ends at an immutable image in ECR. Deployment is a separate, later step for all three environments — prod never triggers a build at all; it re-resolves and deploys the exact image a human already approved.

Choosing what runs, by hand

Every dispatchable file exposes its checks as individual toggles, not one all-or-nothing switch — so a manual run can be as heavy as a full release candidate or as light as "just re-check Semgrep." That's on top of Use workflow from: Branch — GitHub's own selector, present automatically on every one of these four files because each carries a workflow_dispatch trigger. It lists every branch that has the file (develop, uat, release/**, main, any feature/**), and runs that branch's copy of the workflow — nothing extra to configure per branch, it's inherent to the trigger. ci.yml carries the most inputs; the three deploy pipelines each carry a smaller version of the same idea.

Trigger matrix

Eight files, each with exactly one job. Reusable files never trigger on their own — they only run when another workflow calls them.

File & folder structure

Flat under .github/workflows/ on purpose — GitHub only resolves local reusable-workflow references (uses: ./.github/workflows/…) at that one level, so subfolders there would silently break the uses: lines. The reusable- prefix is what keeps a flat folder scannable.

wanda-altcloud/ # true repo root — origin remote lives here ├── .pre-commit-config.yaml # gitleaks, stages: [pre-commit], repo-wide ├── .gitleaks.toml └── .github/ ├── dependabot.yml # pip (strata.* glob) + docker (per service) + github-actions └── workflows/ ├── ci.yml # orchestrator: push/PR → develop, uat, feature/** ├── reusable-app-tests.yml # unit + smoke, language auto-detect, HTML report ├── reusable-secops-scan.yml # semgrep · codeql · trivy-fs · gitleaks backstop ├── reusable-build-scan-push.yml # build · trivy image · grype · sbom · cosign · ECR push ├── reusable-ecs-deploy.yml # render task def · ecs deploy · smoke test ├── deploy-develop.yml # auto after ci.yml on develop, + manual dispatch ├── deploy-uat.yml # auto after ci.yml on uat, + manual dispatch └── release-deploy-prod.yml # push: release/** → manual approval → prod, deploy-only

Guardrails this earns

Build once, deploy three times

Every environment runs the exact bytes that were scanned. Nothing rebuilds between develop, uat, and prod — the tag is the proof.

A human sits between UAT and prod

The prod GitHub Environment carries required reviewers. release-deploy-prod.yml can't proceed past the approval job without one.

Security can fail the build, not just report it

reusable-secops-scan.yml is a gate, not a dashboard — its job fails the caller when a finding crosses the configured severity, before any image gets built.

A broken app fails before it's ever built

reusable-app-tests.yml gates build-scan-push exactly like security does — unit tests and a smoke check against /health, so no image gets built from code that doesn't even start.

One scan definition, eight services

Both reusable files take a service/path input and run once per changed service via a matrix — new services opt in by adding a matrix row, not a new file.

Manual is never a dead end

Every automatic trigger has a workflow_dispatch twin, so a redeploy or a re-run never depends on manufacturing a new commit.

The registry is the audit trail

Cosign-signed, SBOM-attached, immutably tagged <branch>-<sha> images mean "what's running in prod" is always answerable from ECR alone.
