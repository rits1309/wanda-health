Terraform Pipeline Blueprint

The infra companion to the application pipeline: one branch-driven Terraform run per environment, gated by the same gitleaks-before-Checkov-before-plan discipline, with production locked to a human-approved manual apply and nothing else.

  • root: wanda-altcloud-infra-code/.github/
  • environments: develop uat prod
  • workspace: = branch name
  • state: S3, workspace-keyed
  • modules: 14, one AWS surface each

How a branch becomes infrastructure

Every environment gets its own file — terraform-develop.yaml, terraform-uat.yaml, terraform-prod.yaml — none of them offer an environment dropdown, so a manual run can never accidentally target the wrong one. A pull request runs the chain up to plan only, for review; a push (a PR landing) runs the same chain through apply, with no approval gate on develop or uat. Production's file has no push or pull_request trigger at all — reachable only by hand, one gate standing between a click and real infrastructure.

What the dry run actually found

Two real defects surfaced by running the pipeline for real, not by reading the YAML — the kind of thing a plan-only PR is for.

✓
Trivy's tag needed a v prefix.

aquasecurity/trivy-action@0.28.0 doesn't resolve — the repo's tags are v0.28.0. First run failed at security-scan with "unable to find version"; repinned to @v0.36.0, reran, passed.

✓
A tfvars file had reached git history.

environments/dev.tfvars was committed early on, then removed once tfvars moved to S3-at-runtime — but removal doesn't erase history. No secrets were in it, so no rewrite was needed, but .gitignore only matched one path shape and *.auto.tfvars was commented out. Broadened the ignore rule and added a precheck step that fails the run outright if any .tfvars file is ever tracked — a backstop .gitignore alone can't provide, since git add -f ignores it.

Trigger matrix

Six files. Three are reusable and never trigger on their own; the other three are entry points, one per environment, each carrying its own workflow_dispatch for manual runs.

FileTriggerGateDoes
terraform-develop.yaml push / pull_request: develop+ workflow_dispatch none Resolves the action from the event, then calls precheck, security-scan and terraform, hardcoded to develop. PR = plan only; push = apply.
terraform-uat.yaml push / pull_request: uat+ workflow_dispatch none Same shape as terraform-develop.yaml, hardcoded to uat instead.
terraform-prod.yaml workflow_dispatch only — no push, no pull_request prod required reviewers Same three-stage call, hardcoded to prod. GitHub pauses the terraform job until a reviewer approves.
pre_check.yaml called only workflow_call Fails if any .tfvars file is tracked in git; blocks destroy on prod.
security_scan.yaml called only workflow_call Gitleaks (secrets), Checkov (IaC misconfiguration), Trivy config scan. Soft-fail — reports upload either way, findings don't yet hard-block.
terraform.yaml called only workflow_call OIDC auth, fetches environments/<env>.tfvars from S3, init → fmt → validate → plan, then apply/destroy only if the caller asked for it.

Guardrails this earns

No dropdown, ever

Each environment has its own file with the workspace hardcoded in — not read from a picker, not inferred from a ref. A manual dispatch on terraform-develop.yaml structurally cannot touch uat or prod.

Prod has no accidental door

Every other environment reacts to a push. Production doesn't listen for one at all — terraform-prod.yaml only exists as a manual dispatch, gated again by required reviewers on top of that.

Plan is always a separate, visible step

Even on the unrestricted develop/uat path, apply only fires from a real push — a pull request never does more than show you the plan.

Gitleaks runs twice

Once locally before the commit exists at all, once again in CI as a backstop for anyone who skipped or bypassed the hook.

tfvars can't reach git, twice over

.gitignore stops the accident; a dedicated precheck step stops the git add -f that ignores .gitignore.

ECR tags stay immutable without breaking bootstrap

Every task definition previously pointed at :latest against an immutable-tag registry that would only ever accept it once. A bootstrap_image_tag variable replaces it — pushed once per repo, then never touched again.
